# Laporan Kelayakan F5.3 — Offline Kasir

Tanggal: 2026-10-18 · Status: **DIPUTUSKAN OWNER 2026-10-18 — BANGUN** (cakupan v1 sesuai bagian "Rancangan bila dibangun")

## Pertanyaan spike

Apakah antrean transaksi lokal + sinkronisasi (konflik stok, nomor struk per
perangkat, pembayaran) dapat dibuat aman untuk internet mati berjam-jam?

## Metode

Mesin sinkronisasi prototipe (BUKAN kode produksi; berkas spike di luar repo)
menjalankan antrean niat transaksi offline lewat **SalesService asli** —
satu-satunya jalur stok/jurnal — dengan aturan:

- Setiap niat membawa `client_uuid` (idempotensi), `device_id`, nomor struk
  lokal per perangkat, dan cap waktu offline.
- Sinkronisasi berurutan waktu-offline. Penjualan server menerima nomor
  kanonis dari penomoran server yang ada; nomor lokal perangkat disimpan
  sebagai referensi silang (di prototipe: di catatan transaksi + peta lokal).
- Pembayaran non-tunai dalam antrean → **antrean pengecualian** (QRIS/EDC
  tidak dapat dikonfirmasi tanpa jaringan), bukan penjualan.
- Pelanggaran stok tipe ketat saat sinkron → **antrean pengecualian** untuk
  resolusi staf; tipe lunak mengikuti mekanisme backorder FIFO (F4.2).

## Hasil terukur (skenario konflik 2 perangkat, stok frame 2, lensa 1)

| Niat | Isi | Hasil sinkron |
|---|---|---|
| u-1 (KSR1) | frame ×2 tunai | ✅ penjualan (stok frame → 0) |
| u-2 (KSR2) | frame ×2 tunai | ⚠️ pengecualian `rejected` — stok tidak pernah negatif |
| u-3 (KSR1) | lensa ×3 tunai | ✅ penjualan — saldo −2 = backorder sah, ditutup penerimaan berikutnya oleh FIFO |
| u-4 (KSR2) | lensa ×1 QRIS | ⚠️ pengecualian `non_cash_offline` |
| sinkron ulang antrean sama | — | ✅ **nol duplikasi** (idempotensi client_uuid terbukti) |

- Nomor server tetap unik & berurutan; nomor lokal KSR1-000101 terlacak ke
  penjualan servernya.
- **Throughput:** 50 penjualan antrean tersinkron dalam **5,41 detik
  (≈108 ms/penjualan)** di lingkungan uji — antrean seharian ±200 transaksi
  ≈ 22 detik. Bukan penghambat.

## Rancangan bila dibangun

1. Kolom `client_uuid` unik pada penjualan + tabel registri perangkat
   (token per perangkat, dapat dicabut).
2. Klien kasir offline-first (PWA): katalog & harga dibekukan sebagai
   snapshot saat terakhir online; antrean lokal IndexedDB/SQLite; hanya
   TUNAI yang final offline — metode lain tercatat "menunggu konfirmasi".
3. UI resolusi pengecualian: daftar niat tertolak (stok habis / non-tunai)
   dengan aksi staf (jadikan piutang, batalkan, hubungi pelanggan).
4. Sesudah outage panjang: anjuran opname cepat cabang terkait (F4.1 sudah
   menyediakan siklusnya) untuk rekonsiliasi fisik.
5. Endpoint sinkron memakai pola transaksi + lockForUpdate yang sama yang
   sudah lolos suite konkurensi 6 skenario.

## Nilai bisnis, biaya, risiko, kompleksitas

- **Nilai:** toko tetap menjual saat internet mati berjam-jam — menghilangkan
  risiko berhenti-operasi total & catatan manual yang rawan selisih.
- **Biaya:** tanpa layanan baru; satu kali pembangunan klien + endpoint.
- **Risiko:** (a) disiplin kas tunai offline (dimitigasi laporan per
  perangkat); (b) kekecewaan pelanggan bila item ketat ternyata habis saat
  sinkron (dimitigasi peringatan stok snapshot di UI offline); (c) perangkat
  hilang → token perangkat dicabut, antrean belum sinkron hilang (dimitigasi
  sinkron oportunistik tiap jaringan muncul).
- **Kompleksitas:** SEDANG–TINGGI, tetapi hampir seluruhnya di sisi klien &
  endpoint sinkron; invariant server (stok tak negatif untuk tipe ketat,
  jurnal konsisten, idempotensi) SUDAH terbukti oleh spike + suite yang ada.
